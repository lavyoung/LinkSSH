# ADR-0002：桌面端采用资源键驱动的中英文国际化

- 状态：Accepted
- 日期：2026-11-17
- 决策者：LinkSSH Maintainers

## 背景

LinkSSH 桌面端在教程第 1-2 节开始增加 Header、ActivityBar、设置弹窗和多个
工作面板。若继续在 React 组件中直接写入中文文案，后续支持英文时需要逐页
查找和迁移文案，容易产生遗漏、重复键和中英文界面混杂。

国际化属于跨页面基础设施，应在界面规模扩大前确定资源组织、语言检测和
持久化边界。

## 决策

1. 桌面端使用 `i18next` 与 `react-i18next` 管理用户可见界面文案。
2. 首期语言为简体中文 `zh-CN` 和英文 `en-US`，默认使用简体中文。
3. 语言选择保存在本地客户端存储中，只保存语言标识，不保存用户或凭据数据。
4. 翻译资源按稳定业务语义分区，初期使用单一 `translation` 命名空间；只有在
   资源规模确实增长后，才按 `app`、`host`、`execution`、`agent` 等命名空间拆分。
5. React 组件不得直接硬编码新增的用户可见文案，应使用语义化资源键，例如
   `settings.appearance.theme`，不得使用中文原文作为键。
6. 主机名、命令、终端输出、文件路径、协议字段、用户输入和后端原始错误不做
   静态翻译。后端错误后续通过稳定错误码映射为本地化界面消息。
7. 日期、时间、数字和复数优先使用 `Intl` 与 i18next 插值能力，不自行拼接
   特定语言的句子。

## 后果

### 正面影响

- 新页面从创建时即具备中英文能力，避免后期大规模搬迁硬编码文案。
- 翻译资源和业务数据边界清晰，便于校对和自动化检查。
- 未来增加其他语言时不需要改变组件接口。

### 代价与风险

- 增加两个前端依赖及一层资源键维护成本。
- 资源键重命名需要同时修改组件和所有语言资源。
- 早期过度拆分命名空间会增加认知负担，因此暂不按每个组件创建资源文件。

## 备选方案

### 自行实现对象字典与 Context

初期代码量看似更少，但需要自行处理订阅更新、插值、复数、回退语言和持久化，
长期维护成本更高，因此不采用。

### 等界面完成后统一国际化

会使硬编码文案散落在组件和演示数据中，迁移风险随页面数量增加，因此不采用。

## 验证方式

- `npm run build` 必须通过。
- 切换 `zh-CN` 与 `en-US` 后，已接入的界面文案应立即更新。
- 重启桌面应用后保留语言选择。
- 新增界面代码评审时检查是否存在应国际化的硬编码用户文案。

## 重新评估条件

- 需要支持第三种语言。
- 翻译资源增长到单一命名空间难以维护。
- 需要由外部翻译平台或远程资源动态下发文案。
