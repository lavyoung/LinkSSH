# ADR-0005：同时支持自包含桌面与远程服务部署

- 状态：Accepted
- 日期：2026-11-18
- 决策者：LinkSSH Maintainers

## 背景

LinkSSH 目前同时包含 Tauri 桌面客户端和 Java 模块化单体后端。前后端在代码和
进程边界上保持分离，但产品既需要像 VS Code 一样通过一个安装包独立运行，也要
允许桌面客户端连接单独部署的 LinkSSH 服务端。

如果只支持远程服务，个人开发者和离线环境必须额外安装、配置和维护后端及数据
库；如果把全部业务逻辑迁入 Tauri/Rust，则会重复已经建立的 Java DDD、SSH、治理
和审计能力。项目需要在不复制业务核心的前提下支持两种部署拓扑。

教程第 1-4 节开始引入主机配置持久化，因此必须同时确定本地数据库、远程数据源、
凭据存储和进程通信的边界，避免物理表结构反向决定领域模型。

## 决策

### 1. 一个业务核心，两种部署拓扑

LinkSSH 必须支持以下两种并列模式：

```text
                         Tauri + React
                              │
                    REST / SSE / WebSocket
                              │
             ┌────────────────┴────────────────┐
             │                                 │
      自包含桌面模式                       远程服务模式
             │                                 │
   Tauri 管理本地 Java 后端              独立部署 Java 后端
             │                                 │
  SQLite + 操作系统密钥链          可替换数据库 + 服务端凭据存储
```

`host`、`execution`、`agent`、`governance` 和 `audit` 等业务模块不得感知部署
模式。差异只能通过 Bootstrap 装配、Infrastructure Adapter 和客户端 Endpoint
配置表达，禁止在领域模型或应用用例中散布 `localMode`、`serverMode` 分支。

### 2. 自包含桌面模式

完整桌面安装包必须包含：

- Tauri 与 React 客户端
- LinkSSH Java 后端制品
- 应用所需的精简 Java 21 Runtime
- SQLite JDBC 运行依赖
- 数据库迁移脚本

用户不得被要求另行安装 JDK、MySQL、Docker 或 LinkSSH 服务。Tauri 原生进程
负责启动、健康检查和优雅关闭本地 Java 后端。Java Runtime、后端制品和其他只读
运行资源随安装包交付；可变数据写入操作系统应用数据目录，不写入安装目录。

本地后端必须只绑定环回地址和随机端口。Tauri 每次启动生成短生命周期会话凭证，
通过标准输入或其他受控 IPC 传递；该凭证不得进入命令行、日志、数据库或前端
持久化存储。React 不获得任意 Shell、文件系统或凭据访问权限。

### 3. 远程服务模式

远程模式下，桌面客户端连接独立部署的 LinkSSH Server，不启动内置 Java 后端。
服务端仍装配同一组业务模块和公开接口契约，但必须提供适合远程访问的身份认证、
授权、TLS、限流、凭据存储和数据源适配器。

远程模式的 SSH 连接从服务端所在网络发起；本地模式的 SSH 连接从用户电脑所在
网络发起。产品和文档必须明确这一网络语义差异。

首期不要求立即实现第二种数据库。远程单机部署可以复用 SQLite；出现真实的多人
并发、备份或高可用需求后，再通过新的 ADR 引入 PostgreSQL 等服务端数据库适配器。

### 4. 统一接口与客户端 Endpoint

本地和远程模式复用 `linkssh-interfaces` 定义的 REST、SSE 和 WebSocket 契约。
桌面端通过统一 `ApiClient` 或等价传输抽象使用当前 Endpoint，不允许业务组件写死
`localhost:8080` 或远程域名。

本地 Endpoint 由 Tauri 在启动后端后发现；远程 Endpoint 由用户显式配置。远程
连接失败时不得静默切换到本地模式，因为两种模式的数据、身份和凭据归属不同。

### 5. 本地持久化使用 SQLite

自包含桌面模式采用 SQLite 保存非敏感持久化数据。SQLite 文件只能由 Java 后端
的 Infrastructure Adapter 访问；Tauri 和 React 不得直接读写该文件。

本地数据库适合保存：

- 主机配置、分组和标签
- 凭据引用
- 已确认的主机指纹
- 非敏感用户偏好
- 治理策略、审批记录和审计记录

数据库不保存密码、私钥、模型 Token 或其他凭据正文，也不持久化当前运行中的
`ClientSession` 或瞬时连接状态。表结构通过版本化迁移管理，不依赖启动时自动
推断或修改生产结构。

### 6. 凭据存储保持可替换

领域模型和普通关系表只保存 `CredentialReference`。凭据正文通过明确的
`CredentialStorePort` 或等价端口取得：

- 桌面本地模式默认使用操作系统密钥链
- 远程服务模式使用受控服务端 Vault 或等价秘密存储

不得为了复用 Repository 而把加密后的密码或私钥列加入主机配置表；不得提供
允许明文保存的 `encrypted=false` 降级开关。具体跨平台密钥链库和服务端 Vault
产品在实现相应 Adapter 前另行评估。

### 7. 数据归属与同步边界

本地数据和远程数据首期相互独立。切换 Endpoint 不自动复制、合并或双写主机、
凭据、审批和审计数据。需要迁移时使用显式导入导出流程；实时同步、离线冲突合并
和多租户商业化不在当前范围。

“离线部署”表示不依赖 LinkSSH 远程服务和外部数据库。SSH 仍需访问目标主机；
云模型仍需模型网络，除非未来通过独立决策引入本地模型适配器。

### 8. 首期装配策略

首期保留一个 `linkssh-bootstrap` 业务装配制品，通过受控运行配置选择桌面本地或
远程服务装配。若两种拓扑的启动、依赖裁剪和发布生命周期出现显著差异，再通过
ADR 评估拆分独立 Bootstrap 制品，不能提前复制业务模块。

## 后果

### 正面影响

- 用户可以通过一个安装包获得不依赖远程服务的完整桌面体验
- 企业或多设备场景仍可独立部署服务端并复用相同客户端
- Java DDD、SSH、治理和审计能力只维护一份
- SQLite 免除桌面用户安装和维护数据库服务的成本
- Repository、Credential Store 和 API 契约为未来替换适配器保留边界
- 本地与远程网络语义、数据归属和凭据归属保持明确

### 代价与风险

- 桌面安装包需要携带 Java Runtime，体积和构建时间会增加
- Tauri 必须可靠管理 Java 后端的启动、异常退出和关闭
- Windows、macOS 和 Linux 需要分别构建、签名和验证运行资源
- 本地环回 API 仍需短生命周期认证和严格的 Web 安全策略
- SQLite、操作系统密钥链和未来服务端 Adapter 需要独立集成测试
- 两种模式不自动同步，用户切换模式时必须理解数据相互独立

## 备选方案

### 只提供远程服务模式

不采用。个人用户和离线环境需要额外部署服务端与数据库，不符合桌面工具的一次
安装即可运行目标。

### 把全部业务逻辑迁移到 Tauri/Rust

不采用。这会放弃或复制现有 Java 模块化单体、Apache MINA SSHD、Spring AI 和
治理边界，并形成两套领域实现。

### 桌面正式存储使用 H2 内存数据库

不采用。内存数据库在进程退出后丢失数据，不满足主机配置和审计持久化要求。
H2 文件模式技术上可行，但当前没有超过 SQLite 单文件格式、工具生态和桌面适配
性的明确收益。

### 前端或 Tauri 直接访问 SQLite

不采用。这会绕过 Java 应用用例、事务、授权和审计边界，并导致多个进程争用同一
数据库文件。

### 本地与远程模式自动双向同步

不采用。同步需要身份映射、凭据迁移、冲突解决和安全审计，显著超出首期范围。

## 验证方式

- 领域和应用模块不引用 Tauri、SQLite、远程数据库或部署模式类型
- Repository 与 Credential Store 通过内层端口连接基础设施适配器
- 完整桌面安装包可在未安装 JDK、数据库和 LinkSSH 服务的机器上启动
- 本地后端只监听环回地址，并使用随机端口和短生命周期会话认证
- 远程客户端不启动本地后端，并通过相同 API 契约连接服务端
- SQLite 只有 Java 后端一个所有者，数据库中不出现凭据正文和瞬时 Session
- 退出桌面应用后，本地 Java 后端和数据库资源得到释放
- Spring Modulith、ArchUnit、后端测试和桌面构建持续通过

## 重新评估条件

- 两种拓扑无法再由同一 Bootstrap 制品清晰装配
- 远程部署出现经过验证的多人并发、高可用或数据库运维需求
- Java Runtime 使桌面包体积、启动速度或平台发布成本不可接受
- 操作系统密钥链无法满足凭据共享、迁移或企业托管需求
- 用户明确需要本地与远程数据同步或可恢复的离线协作
