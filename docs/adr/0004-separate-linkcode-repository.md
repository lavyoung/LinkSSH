# ADR-0004：将代码智能体作为独立 LinkCode 仓库建设

- 状态：Accepted
- 日期：2026-11-18
- 决策者：LinkSSH Maintainers

## 背景

LinkSSH 当前围绕主机配置、安全 SSH 会话、远程执行、运维 Agent、风险治理和
操作审计建设。项目曾保留未来扩展 Workspace 与代码智能体的可能性，但这些能力
与 SSH 运维工具在核心用户旅程、领域模型、发布节奏和桌面交互上存在明显差异。

如果在 LinkSSH 仓库内继续加入 Workspace、代码理解、代码修改、构建测试和
Coding Agent，产品名称会逐渐失真，模块边界也容易因复用 Agent 基础设施而被
错误合并。现在项目仍处于早期阶段，需要在产生这类耦合前明确产品和仓库边界。

## 决策

### 1. 产品与仓库边界

LinkSSH 继续作为独立产品和仓库，专注于：

- 主机与凭据引用管理
- SSH 会话、终端、命令执行和文件传输
- 面向远程运维的 Agent 工具
- 命令风险治理、人工审批和操作审计

Workspace、代码理解、代码编辑、构建测试和 Coding Agent 由未来独立的
LinkCode 仓库承载，不作为 LinkSSH 的 Maven 模块、Java 包或桌面端子功能加入。

### 2. 命名空间

两个产品可以统一使用组织级 Maven Group ID `com.lavyoung.ai`，但分别使用独立
基础包和制品名称：

```text
LinkSSH  → com.lavyoung.ai.linkssh
LinkCode → com.lavyoung.ai.linkcode
```

两个仓库独立管理版本、发布、CI、桌面应用和项目规划。

### 3. 复用策略

当前不创建第三个公共仓库，也不提前提取 Agent、DTO、工具类或 shared-kernel
作为跨仓库依赖。少量构建规范和架构约定允许分别维护，避免尚未稳定的抽象把
两个产品绑定在同一发布周期。

只有在两个仓库已经出现稳定、语义一致并持续复用的能力后，才通过新的 ADR
评估公共制品。公共制品必须保持产品无关，不能反向依赖任一产品领域模型。

### 4. 产品间协作

未来确有 LinkCode 调用远程执行能力的需求时，优先通过明确授权的 MCP、HTTP API
或其他稳定协议协作，而不是直接依赖 LinkSSH 的内部模块。跨产品调用仍必须经过
LinkSSH 的治理、审批和审计边界。

## 后果

### 正面影响

- LinkSSH 的名称、用户旅程和领域边界保持一致
- LinkCode 可以按代码智能体的需求独立设计 Workspace 和工具权限
- 两个产品能够独立发布、演进和选择技术实现
- 避免共享 Agent 基础设施导致跨产品领域耦合
- 当前 SSH 教程和已经建立的包名、模块名无需迁移

### 代价与风险

- 两个仓库会暂时重复少量构建和工程规范
- 跨产品能力需要维护稳定协议和版本兼容性
- 未来提取真正公共能力时需要额外的制品发布流程
- 两个桌面产品的体验一致性需要通过设计规范而非源码共享维护

## 备选方案

### 将 LinkSSH 重命名为综合 Agent 产品

不采用。该方案可以在单仓库内承载 SSH 和代码能力，但会形成跨度过大的产品边界，
并让远程运维与本地代码工作区共享不必要的发布和权限模型。

### 在 LinkSSH 内新增 Workspace 和 Code Agent 模块

不采用。这会把独立产品能力误当成同一限界上下文的扩展，并增加模块依赖、桌面
导航和安全权限的复杂度。

### 立即提取公共 Agent 平台仓库

不采用。当前只有 LinkSSH 的真实实现，没有足够证据确定稳定公共抽象；提前提取
容易形成低内聚的通用平台和跨仓库联动发布。

## 验证方式

- `PROJECT_PLAN.md` 明确 LinkSSH 与 LinkCode 的产品边界
- LinkSSH 模块列表不包含 Workspace、Code Agent 或 LinkCode 模块
- Java 基础包继续保持 `com.lavyoung.ai.linkssh`
- 新增代码智能体需求时转入独立 LinkCode 规划，不修改 LinkSSH 内部边界
- 跨产品集成不得访问 LinkSSH 的 `internal` 包

## 重新评估条件

- 两个产品出现经过验证的稳定公共能力，并且重复维护成本显著增加
- LinkCode 需要以受治理方式调用 LinkSSH 的远程执行能力
- 两个产品需要统一安装、发布或账号体系，且独立仓库造成不可接受的交付成本
